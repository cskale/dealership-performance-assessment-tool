Action Plan Generation Logic

How the platform turns assessment answers into targeted improvement actions
Product: Dealer Diagnostic Platform Version: June 2026 Audience: Stakeholders & Presentations

1 Overview

When a dealer completes an assessment, the platform automatically generates a prioritised action plan. The entire process is deterministic — the same answers always produce the same actions. There is no AI/ML, no randomness, and no manual intervention required.

The engine analyses each answer, identifies signals (patterns of operational weakness), matches them to pre-built action templates, and enriches each action with consulting-grade context before saving to the database. The dealer and their coach see the finished action plan immediately.

3 Step-by-Step Explanation

Step 1 — Assessment Completion

A dealer answers 61 scored questions across five departments: New Vehicle Sales, Used Vehicle Sales, Service, Parts & Inventory, and Financial Operations. Each answer is a score from 1 (lowest) to 5 (highest). Each question also carries a weight (1.0× to 1.5×) that reflects how much business impact that area has.

Step 2 — Rate Limiting

Before generating, the platform checks a server-side rate limit: a user can generate actions at most 5 times per hour. This prevents accidental duplicate runs and protects infrastructure. The check happens via a Supabase Edge Function.

Step 3 — Signal Generation

The Signal Engine scans every answer. Any question scored 3 or below is flagged as a weakness. The engine then determines what type of weakness it is by resolving a signal code — a standardised label like "PROCESS_NOT_STANDARDISED" or "KPI_NOT_REVIEWED".

Resolution uses a 3-tier fallback:

  1. Tier 1 — Question-level: The question itself declares its signal code (most precise, zero-maintenance).
  2. Tier 2 — Mapping table: A central lookup table maps question IDs to signal codes.
  3. Tier 3 — Category derivation: If neither above matches, the question's category (e.g. "inventory", "digital") is mapped to a signal code automatically.

Weak answers with the same signal code in the same department are grouped together into a single signal. This grouping is important — it means "three weak inventory questions" becomes one strong inventory signal, not three separate alerts.

Step 4 — Severity & Escalation

Each signal is assigned a severity based on the worst score and the question weight:

ConditionSeverity
Score ≤ 2 and weight ≥ 1.3×HIGH
Score ≤ 2 and weight ≥ 1.0×MEDIUM
Score = 3LOW

Escalation rule: If 3 or more questions trigger the same signal, severity is bumped up one level (LOW → MEDIUM, MEDIUM → HIGH). This catches systemic problems that individually look moderate but collectively are serious.

Step 5 — Ceiling Pass (High Performers)

For departments already scoring well (≥65), the engine looks for high-weight questions scored exactly 4. These create soft "ceiling" signals — opportunities for a strong department to reach the next level. This ensures high-performing dealers still get useful, aspirational actions instead of an empty plan.

Step 6 — Template Selection

Each signal is matched to one or more action templates from a library of 22+ pre-built templates. Selection uses a 4-pass cascade:

  1. Tiered templates — Department-specific templates (e.g. "NVS Lead Response", "SVC Workshop Utilisation") matched by score band (foundational / developing / optimising). These are the most tailored.
  2. KPI-specific templates — Templates linked to specific KPIs that overlap with the signal's linked KPIs.
  3. Generic signal templates — Broader templates that match the signal code alone.
  4. Emergency fallback — If all above return nothing, any unbanded template for the signal code is used to guarantee at least one action.

Templates are also filtered by business model (2S sales+service, 3S +parts, 4S +bodyshop) so a 2S dealer never gets a parts-specific action.

Each template already contains: a title, description, owner role, timeframe, priority level, step-by-step implementation instructions with role assignments, and linked KPIs.

Step 7 — Context Intelligence Enrichment

Before saving, each action is enriched with consulting-grade context:

  • Action Context — a plain-language explanation of what the gap is and why it matters, using real industry benchmarks (e.g. "top-quartile labour utilisation: 85–92%").
  • Business Impact — quantified consequences of inaction (e.g. "typically costing 3–5% in recoverable revenue").
  • Root Cause Analysis — identifies whether the issue is people, process, tools, structure, or incentives.
  • Likely Drivers & Consequences — upstream causes and downstream effects.
  • Impact / Effort / Urgency scores (1–5) — helps dealers prioritise which actions to tackle first.
  • KPI Interdependencies — from a database of 111 KPI definitions, showing which metrics this action will affect.

Step 8 — Cross-Validation

The engine runs consistency checks between related answers. For example, if a dealer claims high customer satisfaction but scores poorly on all service-process questions, the system flags this contradiction. These alerts appear alongside the action plan as advisory notes.

Step 9 — Save & Present

Actions are formatted for storage: titles are cleaned, owner roles assigned, due dates calculated from the template's default timeframe, and the full set (max 10 actions) is inserted into the database. A DB trigger automatically logs every insert into an audit trail.

The dealer immediately sees their action plan on:

  • Kanban board — drag-and-drop between Open / In Progress / Completed
  • Roadmap view — actions grouped into 30 / 60 / 90-day columns
  • Action detail panel — full context, implementation steps, activity feed
  • PDF / Excel export — for offline use and reporting

4 The 8 Signal Codes

Every operational weakness detected by the engine maps to one of these eight signal codes:

PROCESS_NOT_STANDARDISED
SOPs missing or inconsistent
PROCESS_NOT_EXECUTED
Defined processes not being followed
ROLE_OWNERSHIP_MISSING
Accountability and ownership gaps
KPI_NOT_DEFINED
Performance metrics not established
KPI_NOT_REVIEWED
Metrics exist but aren't acted on
CAPACITY_MISALIGNED
Resources don't match demand
TOOL_UNDERUTILISED
Technology not fully leveraged
GOVERNANCE_WEAK
Oversight structures insufficient

5 Score Bands & Template Tiers

The department's overall score determines which tier of template is selected, so actions are calibrated to the dealer's maturity level:

Score RangeBandTemplate Tone
0 – 45FoundationalBuild the basics — create SOPs, define roles, establish KPIs
46 – 69DevelopingImprove execution — enforce processes, monitor compliance, train staff
70 – 84OptimisingFine-tune — optimise throughput, leverage data, refine governance
85 – 100CeilingLast-mile improvements — soft signals only, aspirational actions

6 Key Design Properties

Deterministic
Same answers always produce the same signals and actions. No AI, no randomness. Fully auditable and reproducible.
Idempotent
Running the generator twice on the same assessment is safe — it checks for existing actions and skips if already generated.
Business-Model Aware
Templates are filtered by dealership type (2S/3S/4S) so irrelevant actions are never shown.
KPI-Linked
Every action is connected to specific KPIs from a 111-KPI database, showing exactly which metrics will improve.
Maturity-Calibrated
A struggling department gets "build the basics" actions; a strong one gets "fine-tune" actions. Same signal, different prescription.
Rate-Limited
Server-side rate limiting (5 per hour) prevents abuse. Feature flag allows disabling auto-generation entirely.
Audit-Trailed
Every action creation and status change is automatically logged by a database trigger. No client-side logging needed.
Coach-Visible
Actions are visible to the dealer's assigned coach in real-time. Both parties can edit, comment, and track progress.

7 Worked Example

A dealer scores poorly on three Service department questions:

QuestionScoreWeight
"How consistently are service appointments scheduled using the DMS?"21.3×
"Is workshop loading monitored against available capacity daily?"21.2×
"Are service advisors following the vehicle health check process?"31.0×

What happens:

  1. All three questions resolve to signal CAPACITY_MISALIGNED in the service-performance module via Tier 1 resolution.
  2. They are grouped into one signal with severity initially HIGH (score 2, weight 1.3×).
  3. With 3 triggering questions, escalation applies — but severity is already HIGH, so it stays HIGH.
  4. The tiered lookup maps service-performance::CAPACITY_MISALIGNED to the SVC_WORKSHOP_UTILISATION tiered template.
  5. If the Service department score is 52 (band = "developing"), the developing-tier version of that template is selected.
  6. The template is enriched with Context Intelligence: benchmark data ("top-quartile labour utilisation: 85–92%"), root cause ("absence of data-driven capacity planning"), and impact/effort/urgency scores.
  7. Result: one high-priority action titled something like "Implement data-driven workshop capacity planning" with 6 implementation steps, assigned to the Workshop Controller, due in 30 days.
